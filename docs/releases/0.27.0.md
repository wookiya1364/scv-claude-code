# 0.27.0

Core 0.27.0 을 싣고, 이 저장소에서 두 번 손이 갔던 자리 두 곳을 고칩니다.

## 승격이 3초 만에 포기하던 것

0.26.0 승격에서 워크플로가 두 번 조기 종료했고, 두 번 다 손으로 머지했습니다.

경로 필터로 건너뛴 매트릭스 잡은 **확장되지 않은 이름 그대로** 목록에 오르고, 진짜
잡보다 먼저 도착합니다. 대기 조건이 "체크가 몇 개 존재하는가" 였으므로 개수는 즉시
1이 되고, 대기가 끝나고, `gh pr checks --watch` 는 "완료된 항목 하나" 를 보고 성공을
돌려주고, 필수 체크가 생기기도 전에 머지가 거부됩니다.

이 블록이 틀린 건 두 번째입니다. 그전엔 "체크가 통과했는가" 를 물었는데
`gh pr checks` 는 하나라도 대기 중이면 0이 아닌 값으로 끝나므로 대기 내내 "아직"
으로 읽혔습니다. 두 오답이 서로 반대 방향이라, 세 번째 자작 조건을 만드는 대신
머지를 결정하는 값(`mergeStateStatus`)을 봅니다.

세 가지가 함께 성립해야 머지합니다 — 실패한 체크가 없고, 도는 체크가 없고, GitHub 이
`BLOCKED` 이라 하지 않을 것. `CLEAN` 하나만 요구하면 아까 그 자리표시자가 rollup 을
계속 `UNSTABLE` 로 붙잡아 아무것도 머지되지 않습니다.

> 이 수정은 **다음** 승격부터 듣습니다. `workflow_dispatch` 는 기본 브랜치의 워크플로
> 파일을 실행합니다.

## 벤더 게이트

0.25.0 과 0.26.0 모두 릴리스 브랜치에서 Core 를 손으로 심었고, 봇이 연 동기화 PR 은
도착하자마자 "이미 반영됨" 이 되어 닫혔습니다.

문제는 중복이 아니라 **두 경로가 같은 일을 하지 않는다**는 것입니다. 봇은 게시된
릴리스 아티팩트를 해석해 canonical 과 materialized 해시를 둘 다 기록합니다. 손으로
복사하면 그 시점 작업 트리에 있던 것이 기록됩니다. 나중에 둘을 구분할 방법이 없습니다.

이제 봇 브랜치가 아닌 곳에서 `vendor/scv-core/` 를 다시 쓰는 PR 은 머지 시점에
막힙니다. 금지가 아니라 선언입니다 — 제목에 `[manual-vendor: <이유>]` 를 달면
통과합니다. Core 계약이 바뀌면 봇이 못 따라오는 경우가 실제로 있기 때문입니다.

이번 0.27.0 은 봇 PR(#116)을 그대로 머지했습니다.

## Core 0.27.0

위 두 가지의 구현과 검증이 Core 에 있습니다. 덤으로 `check-provenance.sh` 에 처음으로
테스트가 붙었습니다 — 머지를 막는 게이트인데 그동안 검증이 없었습니다.
